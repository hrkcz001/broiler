# Status, 2026-10-25: G7 notification-area icons

Third record for the same day, for gate G7 only: `native tray, one icon per controlled monitor, stable
numeric badges, Per-Monitor V2, hidden top-level owner, version-4 callbacks, Explorer recovery, no GDI
leaks`. [The G6 record](status-2026-10-25-g6.md) and [the storage record](status-2026-10-25-p0-p1.md)
stay as written.

Starting point: `cef31a7`, 252 tests green.

## What was added

`src/tray.rs`, plus a change in how `run_resident` is structured.

- One icon per controlled monitor. The identity comes from the SHA-256 of the monitor id, so the same
  monitor keeps the same tray slot across restarts and an older process cannot leave a duplicate
  behind. Proven by tests: the value is stable and differs per monitor.
- Icons are drawn in-process instead of loaded from assets: a monochrome glyph from a fixed set, with
  an opaque numeric badge in the bottom-right corner when more than one monitor is controlled. The
  badge uses a 3x5 digit table, so 10 renders as `10` and there is no cap at nine. Geometric layout,
  badge composition and the glyph fallback are pure functions with tests.
- Tooltip: index and name, verified profile or `Custom`, and the observed brightness when the reading
  succeeds. Longer than 120 characters is truncated on a character boundary.
- Right click opens a native menu with exactly `Settings` and `Exit`. `Exit` sets the coordinator's
  shutdown flag and ends the message loop, so it stops the whole instance rather than one icon.
  `Settings` says plainly that the settings window is a later gate and prints the profiles path.
- A hidden top-level owner window, not a message-only window, so the `TaskbarCreated` broadcast
  reaches it; on that message every icon is re-added with the same identity.
- Left activation follows `settings.tray.left_click`: `cycle` advances that monitor's profile; the
  `flyout` value is reported as not implemented in this build instead of silently cycling.
- Per-Monitor V2 awareness is declared once per process, shared with the dialogs.

## Structural change

The tray needs a message loop on the UI thread, and the daemon has a blocking accept loop. The daemon
now runs on a worker thread and the UI loop owns the main thread. Two `unsafe impl Send` declarations
were needed and both are documented in place: `Endpoint` owns its security descriptor and ACL and only
moves, and `Handle` was already declared `Send` because Win32 handles are process-wide.

## Bugs found while proving it

1. The first live run died with `0xC0000409` before writing anything to the log. The window procedure
   read the user-data pointer as a newtype wrapper while the window had been given a plain `*mut Tray`,
   so the first bytes of the struct were interpreted as a pointer. Fixed by reading the stored type.
2. `broiler stop` reported success while the process stayed alive. The daemon serves a request on a
   handler thread and then blocks in its next `ConnectNamedPipe`; if the shutdown flag is set after
   that check, nothing ever releases the accept and the tray loop has no reason to end. A watchdog now
   polls the flag, posts `WM_CLOSE` to the tray window and releases the blocked accept with one real
   request. Measured: `stop` returns in 83 ms and the process is gone within a second.
3. `init_logging` passed a constant level, so `settings get logging.level` claimed a verbosity the log
   file did not honour. It now reads the configured level. This is what made the two bugs above
   visible at all.
4. `NIM_SETVERSION` is refused on this machine, immediately after `NIM_ADD` and again after a 400 ms
   retry. The icon itself is accepted. The refusal is logged, and the callback decoder handles the
   packed version-4 `lParam` and the legacy `wParam`/`lParam` packing, so a working icon is kept
   instead of discarded. Version-4 behaviour is therefore **requested but not in effect here**.

## Not verified

- That the icon is visible in the notification area, that a click cycles a profile, that the menu
  opens and that `Exit` closes the instance — all of that needs a hand on the mouse, and the desktop
  was in use during this session. The log proves the shell accepted the icon, not that a user can see
  or use it.
- Explorer restart recovery: the `TaskbarCreated` path exists but was never exercised, because
  restarting Explorer was not acceptable while the machine was in use.
- GDI and handle counts across repeated install/remove cycles: "no GDI leaks" is claimed only as
  "every `HICON` and menu is destroyed exactly once in `Drop`", which is code review, not a
  measurement.
- Two-monitor badges on real hardware: this machine has one controllable external display, so the
  badge geometry is proven by unit tests only.
- DPI changes while running, and the icon at 150/200 %.

## Open item carried forward

`NIM_SETVERSION` refusal deserves a proper look in a later gate: the request is made twice with the
version-3 structure size, the icon is accepted, and the failure has no usable `GetLastError` value
(0x80004005 is stale). Until it is understood, treat version-4 callbacks as unproven.
