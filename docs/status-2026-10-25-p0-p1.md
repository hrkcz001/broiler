# Status, 2026-10-25: production correctness and storage

Follow-up record for the two prerequisite gates in [the next worker handoff](next-worker-handoff.md)
section 4. It states what a command produced, and separates that from what remains unproven. The
handoff and `docs/storage.md` are unchanged above their dated follow-up sections.

Starting point: `168cc78`, 184 library tests green, clean worktree.

## P0: strict preflight, failure boundaries and aggregation

Before the change, `Coordinator::apply_everywhere` applied contrast and brightness with its own loop
and never called the planner in `src/plan.rs`. Reproduced as failures first, with a fake transport:

- `profiles.unsupported = fail` wrote brightness and only then reported volume as unsupported;
- a monitor whose contrast was missing still received brightness under the strict policy;
- a timed-out write did not stop the rest of that monitor's transaction;
- one applied target plus one failed target was reported as `applied`;
- an unknown target id was answered per field instead of being refused up front;
- a direct `set` left the old profile id labelled active.

Now: metadata is read only for the controls a profile requests, `plan::plan` is called for every
target, and nothing is written until all targets are planned. A control with no write path in this
build is reported as `skipped`/`not_implemented`, not as a device limitation. Execution stops on a
monitor once a write is outcome-unknown, remaining fields are marked `not_attempted`, and the result
carries a typed `cause` per monitor and overall. The CLI maps that cause to exit 5 (unsupported or
unimplemented), 2 (invalid value) or 6 (transport, timeout, verification).

Evidence:

```text
MSYS2_ARG_CONV_EXCL='*' cmd.exe /c build.bat test
test result: ok. 234 passed; 0 failed
```

Nine of those tests were written before the fix and failed against `168cc78`; the eleven
coordinator tests concerned are named for the property they hold, for example
`strict_policy_writes_nothing_on_either_target_when_one_target_lacks_a_control` and
`a_timeout_stops_the_rest_of_that_monitors_transaction`.

Not claimed: any physical profile application. No hardware write was performed by this session.

## P1: one storage context, portable marker, copy-only migration

Implemented in `src/storage.rs` and `src/migrate.rs`:

- precedence `--config-dir` → `broiler.portable` beside the executable → AppData; a relative
  explicit path is resolved once; an unusable root is an error with no fallback; an existing `data`
  directory alone never selects portable mode;
- `paths [--json]` and a `storage` block in `status --json` in both the running and not-running case;
- `data migrate --from-appdata [--dry-run | --decline] [--json]`, staged and journalled publication,
  per-file hash recorded, rollback only for a published file whose content still matches, source
  never deleted, destination conflicts stop the whole run, `state.json` refused unless its schema
  version matches;
- a portable first launch with older AppData configuration refuses to start and prints the three
  commands; `start` prints the same message instead of spawning a child that exits;
- a pipe request carries the caller's root; the coordinator refuses a different one with
  `storage_conflict`;
- `settings.set` edits the file on disk with `toml_edit`, validates, and replaces it atomically after
  refusing a stale edit; `settings select`/`settings.save` paths keep their existing atomic write.

Evidence, all on disposable directories:

```text
MSYS2_ARG_CONV_EXCL='*' cmd.exe /c build.bat test          # 234 passed, 0 failed
```

Plus a live check with the release binaries in a disposable portable install (an `app/` directory
holding both executables and an empty `broiler.portable`), run from a different working directory:

- `paths --json` reported `mode: portable` and root `<app>/data`, with the marker path;
- `start` refused with the actionable first-launch message and exit 2, creating nothing;
- `data migrate --from-appdata --dry-run` against the owner's real AppData listed
  `settings.toml`, `profiles/day.toml`, `profiles/night.toml` as absent at the destination, reported
  `logs/` as intentionally skipped, and changed nothing;
- `--config-dir <A> start` started the coordinator, which reported root A in `status --json`;
- `--config-dir <B> status` was refused with `storage_conflict` and exit 2;
- `--config-dir <A> settings set tray.left_click cycle` wrote root A's `settings.toml`;
- `stop` returned `coordinator stopped`, and `status` then reported `not running`;
- no `broiler.exe` or `broiler-tray.exe` process was left running.

The owner's `%APPDATA%\broiler` and `%LOCALAPPDATA%\broiler` were read by the dry run only. Their
timestamps are unchanged and no file was copied out of them.

Not claimed: a real Scoop install, the observed `data` junction target, upgrade or uninstall
retention, the ordering of pre-install hooks against persist linking, autostart registration against
a stable `current` path, and a release archive.
