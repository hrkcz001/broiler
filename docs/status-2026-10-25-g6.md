# Status, 2026-10-25: G6 startup lifecycle

Second follow-up record for the same day. It covers gate G6 only, states what a command produced, and
names what is still missing. Earlier records stay as written: [the P0 and P1 gate record](status-2026-10-25-p0-p1.md),
[the storage contract](storage.md), [the handoff](next-worker-handoff.md).

Starting point for this gate: `f0428e6`, 234 library tests green.

## What was wrong

`runtime::run_resident` served the pipe unconditionally. The startup decision in `src/lifecycle.rs`
was pure, tested and reachable through the `startup.status` method, but no launch path consulted it:
`broiler start` and the no-argument tray both became resident even with no controllable monitor, a
single profile was never applied at logon, and a multi-monitor machine with no recorded choice was
silently treated as a resident with no targets. `lifecycle::decide` also had no mapping from an
outcome to an action, so nothing forced the two entry points to agree.

## What it does now

`runtime::plan_startup` maps every outcome to one action, and `runtime::startup_step` executes it:

| outcome | action |
| --- | --- |
| `no_controllable_monitors` | exit 0, silent, no dialog, no tray |
| `empty_selection` | exit 0, silent |
| `invalid_profiles` | exit 2, diagnostics point at `profiles validate` |
| `selection_required` | exit 2 without writing; the message names `monitors select` |
| `zero_profiles` | exit 2 without inventing a profile; the message names the directory |
| `one_shot_complete` | apply the one profile to the targets once, then exit with the apply result |
| `resident` | stay resident and serve the pipe |

Both entry points use it: `broiler start` (also the logon entry point) decides first and only spawns
the resident for the `resident` outcome; `broiler-tray.exe` with no arguments decides after loading
the registry and exits before offering the pipe. `Coordinator::startup_outcome` is now the single
implementation of the decision, and `startup.status` reports it through the same call.

The one-shot branch is the only branch that can write, and it writes through `profile.apply`, so it
inherits the planner fixes from the P0 gate rather than a second write path.

## Evidence

```text
MSYS2_ARG_CONV_EXCL='*' cmd.exe /c build.bat test
test result: ok. 241 passed; 0 failed
```

Seven new tests in the `runtime` module, all against the fake transport: no monitor exits silently
with no writes, a single profile writes exactly the profile value once and returns `Exit(0)` rather
than `Serve`, a single profile the monitor does not offer returns `Exit(5)` with no write, several
profiles stay resident with no writes, two monitors without a recorded choice return `Exit(2)` with
no writes, zero profiles return `Exit(2)` with no writes, and every outcome maps to the expected
action.

Live run with the release binaries in a disposable portable install (an `app/` directory holding both
executables and an empty `broiler.portable`, data root selected with `--config-dir`):

- empty `data/profiles`: `start` printed `there is no profile in ... , so there is nothing to apply`,
  exit 2, and `status` still said `not running`;
- two profiles: `start` printed `coordinator started`, exit 0, and `startup status` reported
  `"outcome": "resident"` with the single target; `stop` then returned `coordinator stopped` with no
  profile applied;
- one profile: `start` printed `mon-227062c49310910f: night applied` and `brightness applied`,
  exit 0, and `status` then reported `not running` — the one-shot path applied once and did not
  become resident.

Hardware contact in that live run: exactly one DDC write, `brightness` on `mon-227062c49310910f`
(MSI MAG275R), performed to prove the one-shot path. It was chosen as the value the monitor already
held so it changed nothing: `get brightness` reported `0` before and `0` after. No other write, no
profile apply, no autostart change.

## Still missing in G6

- The checkbox selection dialog. `selection_required` currently stops the launch with an actionable
  message instead of showing the dialog, so a multi-monitor machine with no recorded choice is not
  yet usable by clicking.
- The minimal zero-profile setup window. `zero_profiles` stops with the directory path; the window
  that would offer "open profiles directory / reload / exit" does not exist.
- Tray icons, which the `resident` branch would need in order to be visible.

G7 onward (tray, flyout and settings windows) is untouched.

## Addendum, same day: the two windows

The two missing surfaces above are now built, which closes the functional part of G6 that a command
can reach. They live in `src/win/ui.rs` and use only User32 standard controls.

- The selection dialog is the checkbox list the contract describes: one row per monitor labelled with
  model, connector and `primary`, a `Remember choice` box, and OK/Cancel. An uncontrollable display is
  listed, labelled `(not controllable)`, disabled, and dropped from the answer even if Windows reports
  it checked.
- The setup window offers exactly `Open profiles directory`, `Reload` and `Exit`, and closing it means
  Exit.
- `broiler monitors select --dialog` opens the dialog explicitly. Cancel records nothing; a confirmed
  empty selection records an empty selection, which is a decision, not a cancellation.
- `runtime::startup_step` now asks instead of stopping, and re-decides afterwards: a confirmed
  selection goes through `monitors.select` so the coordinator's in-memory settings match the file, and
  `Reload` re-reads the registry. Asking is bounded (`MAX_ASK_ROUNDS`) so an unchanging answer cannot
  loop, and Cancel at startup exits 0 as the contract requires.

`startup_step` takes an explicit `Ask` argument. This was not a stylistic choice: the first version
opened the dialog unconditionally, and the test suite hung for three minutes waiting for a click that
can never come in a test run. A decision path that can block on a user is now something a caller has
to ask for, and every test passes `Ask::Never`.

### Evidence

```text
MSYS2_ARG_CONV_EXCL='*' cmd.exe /c build.bat test
test result: ok. 252 passed; 0 failed
```

New tests: the two window-creation tests actually create the windows and inspect them through the
window manager rather than our own state — six child controls for a two-monitor selection dialog
(prompt, two rows, remember box, two buttons) and four for the setup window, plus a non-zero window
rectangle in both cases, then they destroy the windows. The rest cover which identifiers a confirmed
answer records, that a disabled row is never recorded, that a confirmed selection is written without
disturbing the other settings, that an empty selection is recorded as empty, row geometry never
overlapping from 1 to 12 rows at 96/120/144/192 DPI, and that no measurement collapses at low DPI.

### Not verified

Nothing about on-screen use: no click, no keyboard traversal, no Narrator pass, no visual check at
100/150/200 % on a second display, and no at-logon run on a machine with two real monitors. A dialog
was launched once during this session while the desktop was in use and stayed behind a fullscreen
application; it was terminated rather than driven, so "the window appears and can be answered" is
still a manual check for the owner or the next validation session. The window-creation tests are
evidence that the windows are built correctly, not that they are usable.

Launching an interactive dialog from `monitors select --dialog` also blocks until it is answered,
which is correct for a modal dialog but must never happen in an unattended path. The `Ask` argument
covers the automatic path; the explicit command is the user's own request.
