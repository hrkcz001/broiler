## `NIM_SETVERSION`: the refusal was our bug, not the machine's

Microsoft documents the narrow contract: `cbSize` is "the size of this structure, in bytes"
(`NOTIFYICONDATAW`), with the version-2 and version-3 sizes tabulated only for older `Shell32.dll`
versions; `NIM_SETVERSION` "must be called every time a notification area icon is added" and does not
need `NIM_MODIFY` or a delay; a `FALSE` return means "the requested version is not supported" and no
`GetLastError` value is promised; and an icon is identified "either through its `uID` or `guidItem`
member", which is "used in subsequent calls to `Shell_NotifyIcon`".

The previous build passed the version-3 size, `uFlags = 0`, and only `uID`, although the icon had been
added with `NIF_GUID`. Both parts of the identifier were therefore wrong, and the delay-plus-retry was
compensating for a defect rather than an OS quirk.

The repair: `cbSize` is `sizeof(NOTIFYICONDATAW)`, `NIM_SETVERSION` follows each `NIM_ADD` immediately
with `NIF_GUID` and the same `guidItem`, the retry timer and the truncated size are gone, negotiation
is stored per icon, and the decoder routes both documented encodings by each icon's own result
(`tray::tests::a_mixed_set_routes_each_icon_by_its_own_negotiation`). `NIF_GUID` was also added to the
`NIM_MODIFY` calls that lacked it.

Observed on this machine, real run, `logging.level = info`:

```text
2026-10-25 08:57:59.388 [info] startup outcome: resident
2026-10-25 08:57:59.388 [info] coordinator listening on \\.\pipe\broiler.v1.db7223e564eb5ccf (protocol 1)
2026-10-25 08:57:59.404 [info] icon 0 installed for mon-227062c49310910f
```

No refusal line. The G7 run on the same machine logged `the shell refused the version-4 behaviour
(Win32 error 2147500037)` and `version-4 icon callbacks were refused 0/1 time(s)`. That earlier
statement is corrected in `docs/architecture.md` next to the sentence it belonged to.

## Test isolation

`src/pipe.rs` gained a `#[cfg(test)]` fixture module: a thread-local endpoint namespace whose name
contains `.fixture.`, so a fixture endpoint can never equal the logon-SID token the product derives,
and no shipped binary contains a way to name another endpoint at all. `instance.rs` derives the
mutex from the whole endpoint name by hash instead of from one parsed segment, so one endpoint is one
owner. `runtime::request_on` addresses a named endpoint for fixture clients; production still calls
`request`, which resolves the only production endpoint.

Evidence, with a real resident instance holding the production endpoint:

```text
MSYS2_ARG_CONV_EXCL='*' cmd.exe /c build.bat --release      Finished release, 25.15 s
broiler --config-dir <scratch> start                        coordinator started
broiler --config-dir <scratch> status                       running, 1 monitor(s), 2 profile(s)
MSYS2_ARG_CONV_EXCL='*' cmd.exe /c build.bat test           283 passed, 0 failed, 1.40 s
broiler --config-dir <scratch> stop                         coordinator stopped
status                                                      not running; no broiler process remained
```

The same suite previously failed six tests in exactly this situation (reverse handoff, "a test run
fails while an instance is running"). A fixture coordinator on one namespace is also proven invisible
to a client on another (`runtime::tests::one_fixture_namespace_never_answers_another`).

## One hardware write, with reason and before/after

Reason: to prove that a CLI cycle reaches the worker, is verified, and publishes a state change while
the tray is resident. Safety: both profiles were written with the values the monitor already reported,
so the write cannot change what the user sees.

```text
get brightness --monitor mon-227062c49310910f
  brightness 100 (min 0, max 100, dxva2-high-level)          contrast 80 (min 0, max 100)
profile next --monitor mon-227062c49310910f
  mon-227062c49310910f: day applied
    contrast   applied
    brightness applied
```

Before: brightness 100, contrast 80. After: requested 100 and 80, readback matched both. No visible
change was possible, by construction.
